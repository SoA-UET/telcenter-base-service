# H23 Group

## Overview

This is the group of HTTP APIs between the
**Core Portal (Admin Telcenter Core)**
and [**Core Employee Validator Service – S06**](../services/core/S06_Core_Employee_Identity_Service.md).

This API group supports the following use cases:

* **TC-01: Admin Login**

  * **TC-01.1: Standard Login**

* **TC-02: Manage Core Employee Accounts**

  * **TC-02.1: Add Employee Account**
  * **TC-02.2: Update Employee Account**
  * **TC-02.3: Delete / Disable Employee Account**

The APIs are designed following RESTful principles and used exclusively for **Core employee authentication and management**.

## H23 Endpoint 1: `POST /api/v1/core-auth/login`

(**Use Case: TC-01 – Admin Login**)

This endpoint allows **Admin Telcenter Core** or **Telcenter Core's Employees**to log in.

### Actor

Admin Telcenter Core
Core's Employee

### Preconditions

* Account exists and is provided by the system.

### Postconditions

* Logging in successfully.
* Redirecting to the Core management dashboard.

### Request

**Headers**

```
Content-Type: application/json
```

**Body**

```json
{
  "username": "admin_core",
  "password": "Admin@123"
}
```

### Behavior

1. The system validates username and password.
2. If valid, a JWT access token is generated.
3. The Admin is redirected to the Core Dashboard.
4. If login fails **≥ 5 times**, the account is locked for **30 minutes**.
5. If the account is not activated, login is denied.

### Response (HTTP 200 OK)

```json
{
  "status": "success",
  "message": "Đăng nhập quản trị thành công",
  "access_token": "<jwt_token>",
  "token_type": "Bearer",
  "expires_in": 3600,
  "admin": {
    "employee_id": 1,
    "full_name": "Admin Core",
    "role": "ADMIN",
    "status": "ACTIVE"
  }
}
```

### Error Responses

* **HTTP 401 Unauthorized – Invalid credentials**

```json
{
  "status": "error",
  "error_code": "INVALID_CREDENTIALS",
  "message": "Sai tên đăng nhập hoặc mật khẩu"
}
```

* **HTTP 403 Forbidden – Account inactive or locked**

```json
{
  "status": "error",
  "error_code": "ACCOUNT_LOCKED_OR_INACTIVE",
  "message": "Tài khoản bị khóa hoặc chưa được kích hoạt"
}
```

## H23 Endpoint 2: `GET /api/v1/core-employees`

(**Use Case: TC-02 – View Employee Account List**)

This endpoint allows **Admin** to view the list of Core employee accounts.

### Actor

Admin Telcenter Core

### Preconditions

* Admin is authenticated.
* Admin has role **ADMIN**.

### Postconditions

* The employee account list is displayed.

### Request

**Headers**

```
Authorization: Bearer <jwt_token>
```

### Behavior

1. The system validates the JWT token.
2. The system verifies ADMIN role.
3. The system returns a paginated list of employee accounts.

### Response (HTTP 200 OK)

```json
{
  "status": "success",
  "total": 25,
  "employees": [
    {
      "employee_id": 1,
      "full_name": "Admin Core",
      "role": "ADMIN",
      "status": "ACTIVE",
      "created_at": "2025-12-01T08:30:00Z"
    }
  ]
}
```

## H23 Endpoint 3: `POST /api/v1/core-employees`

(**Use Case: TC-02.1 – Add Employee Account**)

This endpoint allows Admin to create a new Core employee account.

### Actor

Admin Telcenter Core

### Preconditions

* Admin is logged in.
* Admin is on the employee management screen.

### Postconditions

* A new employee account is created.
* A default password is generated.
* An activation email is sent to the employee.

### Request

**Headers**

```
Authorization: Bearer <jwt_token>
Content-Type: application/json
```

**Body**

```json
{
  "full_name": "Nguyễn Văn B",
  "role_id": 2,
  "partner_id": null
}
```

### Behavior

1. Validate Admin permission.
2. Check duplicate account information.
3. Create a new employee with a default password.
4. Store account with status **INACTIVE**.
5. Send activation email to the employee.

### Response (HTTP 201 Created)

```json
{
  "status": "success",
  "employee_id": 45,
  "message": "Tạo tài khoản nhân viên thành công và đã gửi email kích hoạt"
}
```

### Error Response

* **HTTP 409 Conflict – Duplicate account**

```json
{
  "status": "error",
  "error_code": "EMPLOYEE_ALREADY_EXISTS",
  "message": "Tài khoản nhân viên đã tồn tại"
}
```

## H23 Endpoint 5: `DELETE /api/v1/core-employees/{employee_id}`

(**Use Case: TC-02.3 – Delete / Disable Employee Account**)

This endpoint allows Admin to **disable or permanently delete** a Core employee account.

### Preconditions

* Admin is authenticated.
* Employee account exists.

### Request

**Headers**

```
Authorization: Bearer <jwt_token>
```

**Optional Query Param**

```
?lock_only=true
```

### Behavior

* Default: **soft delete (disable account)**.
* If `lock_only=true`: temporarily lock the account instead of disabling.

### Response (HTTP 200 OK)

```json
{
  "status": "success",
  "message": "Tài khoản nhân viên đã bị vô hiệu hóa"
}
```
## JWKS

The Customer Identity Service must issue and manage JWT tokens using **RS256** and expose a **JWKS endpoint** for downstream services to validate signatures.
### 1. JWT Signing Requirements

* All JWTs must be signed using **RS256 (RSA SHA-256)**.
* The signing key pair must be associated with a unique **kid**.
* JWT header must include:
  * `alg`: RS256
  * `kid`: active signing key identifier
* JWT must include the following claims:
  * `sub`
  * `name`
  * `email`
  * `permissions`(["permission_1", "permission_2", "..."]),
  * `iat` (Issued At)
  * `exp` (Expiration)
  * `iss` (Issuer)
  * `aud` (Audience)

### 2. JWKS Endpoint

The Identity Service must expose a JWKS endpoint at:

```
{BASE_URL}/.well-known/jwks.json
```

### Requirements

* JWKS must publish **all currently active public keys**.
* Each key entry must contain:

  * `kid`
  * `kty`
  * `alg`
  * `n`
  * `e`
  * `use`: "sig"

Downstream services must retrieve this JWKS to validate JWT signatures.

### 3. Key Rotation

The Identity Service must support both **automatic** and **manual** RSA key rotation.

Rotation workflow:

1. Generate a new RSA key pair.
2. Assign a new `kid`.
3. Add the new public key to the JWKS endpoint.
4. Begin issuing new JWTs signed with the new private key.
5. Continue returning older public keys in JWKS until all previously issued tokens (signed with old keys) have expired.
6. After all tokens tied to the old key have expired:

   * Remove the retired key from JWKS.

This ensures no downstream service rejects tokens that were validly issued before rotation.

### 4. Token Issuance Rules

* All newly issued tokens must use the **latest active** RSA key pair.
* The JWT header must always reference the correct `kid`.
* Token expiration policy must align with key retention policy to prevent premature invalidation.


### 5. Deliverables (Identity Service)

The Identity Service must provide:

* JWKS generation module.
* Key rotation scheduler or CLI tool.
* JWKS endpoint controller.
* Operational documentation describing:

  * Key rotation policy
  * Token lifetime rules
  * JWKS compatibility requirements

## Notes

* All endpoints except **login** require **JWT authentication**.
* **IMPORTANT**: All JWTs issued by the Core Identity Service must be signed using the RS256 algorithm (RSA asymmetric key). The service must sign with a private key and expose the public key to other services for verification.
* Only users with role **ADMIN** are authorized to manage Core employees.
* New employee accounts require **email activation**.
* Rate limiting: **60 requests/minute per admin**.
